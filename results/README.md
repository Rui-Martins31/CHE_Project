# Results

## Profiling with gprof and gcov (checkpoint 1.1)

The aim is to find where `harknn` spends its time, as a basis for the OpenMP and FPGA work.
The profiles are generated by [`scripts/profile.sh`](../scripts/profile.sh) and are **not stored in git** (`results/profiling/` is ignored).
To regenerate them:

```sh
bash scripts/profile.sh wisdm 3 1    # SCENARIO (wisdm|pamap2)  K  DT (1 = double, 2 = float)

# all 12 configurations used below
for s in wisdm pamap2; do for k in 3 5 20; do for dt in 1 2; do
  bash scripts/profile.sh $s $k $dt
done; done; done
```

For each configuration the script builds and runs the program three times:

| Build | Flags | Output | Used for |
|---|---|---|---|
| gprof, optimised | `-O2 -g -pg` | `gprof_O2.txt` | Realistic share of time per function |
| gprof, unoptimised | `-O0 -fno-inline -g -pg` | `gprof_O0.txt` | Complete call graph (no inlined functions) |
| gcov | `-O0 --coverage` | `gcov/*.gcov`, `gcov_summary.txt` | Exact number of times each line and branch runs |

All three use the same `-D` defines as `knn/Makefile` (`READ=4`, `SPECIALIZED=1`, `USE_SQRT=1`, ...).
On Windows (MinGW-w64) the gprof builds also need `-no-pie`; without it gprof prints an empty profile.

Output goes to `results/profiling/<scenario>_k<K>_<double|float>/`.

### Machine

Intel Core Ultra 7 265H (16 threads), Windows 11, GCC 13.2.0 (MinGW-w64, Strawberry Perl).

### Call graph

```
main
 ├─ read_data_points (x2)          file reading, mostly inside the C library
 ├─ minmax_normalize_point (x m)
 ├─ knn_classifyinstance_3 / knn_classifyinstance (x m)
 │   ├─ get_3_NN / get_k_NN        distance to every training point  →  m·n·d operations
 │   │   ├─ sqrt / sqrtf (x n)
 │   │   ├─ select_3_nearest / select_k_nearest   →  ~m·n (k=3) or ~m·k·n (k>3)
 │   │   └─ copy_3_nearest / copy_k_nearest
 │   └─ plurality_voting_3 / plurality_voting
 └─ put (x m)                      stores the predicted class
```

k = 3 uses the specialised `*_3` functions (one pass over the distances); other values of k use the general ones, where `select_k_nearest` is a partial selection sort (k passes).

### Main observations

- **The distance loop in `get_3_NN` / `get_k_NN` is the main hotspot** in almost every configuration.
  gcov confirms it runs m × n times (23.35 M distances for WISDM, 6.24 M for PAMAP2), each over d features.
  This is the main candidate for OpenMP parallelisation and for the FPGA accelerator.
- **Selection grows with k.** `select_k_nearest` makes k passes over all n distances, so for WISDM with k = 20 it becomes the largest hotspot.
  A single-pass selection (as in `select_3_nearest`) or a small sorted buffer would remove most of that cost.
- **`sqrt` is called n times per instance** (about 3–8 % at `-O0`), but it does not change which neighbours are nearest; `USE_SQRT=0` avoids it.
- **float is not faster than double here** with `-O2`. Worth looking at again with vectorisation (`-O3`, `-march=native`).
- **The `-O0` build gives a different picture:** there the distance loop takes 73–93 % even for k = 20, because unoptimised code penalises it more than the selection.

### Limitations

- gprof samples only 100 times per second, and the runs last about 0.2–0.6 s, so the percentages are approximate (± about 10 %) and change between runs.
  The gcov counts are exact.
- gprof does not count time inside the C library, so most of the file-reading time is missing from the profiles.
- The timings come from instrumented (`-pg`) builds and are only indicative; checkpoint 1.2 measurements should use normal builds.
