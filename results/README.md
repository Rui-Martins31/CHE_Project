# Results

## Profiling with gprof and gcov (checkpoint 1.1)

The aim is to find where `harknn` spends its time, as a basis for the OpenMP and FPGA work.
The profiles are generated by [`scripts/profile_gnu.py`](../scripts/profile_gnu.py) and are **not stored in git**.
To regenerate them:

```sh
python scripts/profile_gnu.py wisdm 3 1    # SCENARIO (wisdm, pamap2)  K  DT (1 = double, 2 = float)
python scripts/profile_gnu.py --all        # all 12 configurations used below
```

For each configuration the script builds and runs the program three times:

| Build | Flags | Output | Used for |
|---|---|---|---|
| gprof, optimised | `-O2 -g -pg` | `gprof_O2.txt` | Realistic share of time per function |
| gprof, unoptimised | `-O0 -fno-inline -g -pg` | `gprof_O0.txt` | Complete call graph (no inlined functions) |
| gcov | `-O0 --coverage` | `gcov/*.gcov`, `gcov_summary.txt` | Exact number of times each line and branch runs |

All three use the same `-D` defines as `knn/Makefile` (`READ=4`, `SPECIALIZED=1`, `USE_SQRT=1`, ...).
On Windows (MinGW-w64) the gprof builds also need `-no-pie`; without it gprof prints an empty profile.

Output goes to `results/profiling/<scenario>_k<K>_<double|float>/`.

### Machine where it was tested

Intel Core Ultra 7 265H (16 threads), Windows 11, GCC 13.2.0 (MinGW-w64, Strawberry Perl).

### Call graph

```
main
 ├─ read_data_points (x2)          file reading, mostly inside the C library
 ├─ minmax_normalize_point (x m)
 ├─ knn_classifyinstance_3 / knn_classifyinstance (x m)
 │   ├─ get_3_NN / get_k_NN        distance to every training point  →  m·n·d operations
 │   │   ├─ sqrt / sqrtf (x n)
 │   │   ├─ select_3_nearest / select_k_nearest   →  ~m·n (k=3) or ~m·k·n (k>3)
 │   │   └─ copy_3_nearest / copy_k_nearest
 │   └─ plurality_voting_3 / plurality_voting
 └─ put (x m)                      stores the predicted class
```

k = 3 uses the specialised `*_3` functions (one pass over the distances); other values of k use the general ones, where `select_k_nearest` is a partial selection sort (k passes).

### Main observations

- **The distance loop in `get_3_NN` / `get_k_NN` is the main hotspot** in almost every configuration.
  gcov confirms it runs m × n times (23.35 M distances for WISDM, 6.24 M for PAMAP2), each over d features.
  This is the main candidate for OpenMP parallelisation and for the FPGA accelerator.
- **Selection grows with k.** `select_k_nearest` makes k passes over all n distances, so for WISDM with k = 20 it becomes the largest hotspot.
  A single-pass selection (as in `select_3_nearest`) or a small sorted buffer would remove most of that cost.
- **`sqrt` is called n times per instance**, but it does not change which neighbours are nearest (`USE_SQRT=0` avoids it).
- **float is not faster than double here** with `-O2`.
- **The `-O0` build gives a different picture:** there the distance loop takes 73–93 % even for k = 20, because unoptimised code penalises it more than the selection.

### Limitations

- gprof samples only 100 times per second, and the runs last about 0.2–0.6 s, so the percentages are rounded up and change between runs.
  The gcov counts are exact.
- gprof does not count time inside the C library, so most of the file-reading time is missing from the profiles.
- The timings come from instrumented (`-pg`) builds and are only indicative.

## Profiling with Intel VTune (checkpoint 1.1)

VTune hotspots analysis of the same 12 configurations, generated by [`scripts/profile_intel.py`](../scripts/profile_intel.py):

```sh
python scripts/profile_intel.py --all --no-advisor
```

The program is built with `-O2 -g` (no `-pg`), so the code being measured is the same as a normal optimised build.
VTune uses user-mode sampling (default interval about 10 ms) and, unlike gprof, also samples time inside system DLLs.
Outputs per configuration: `vtune_summary.txt`, `vtune_hotspots.csv`, `vtune_topdown.txt`.

### Comparison with gprof

"I/O" is the time in `ucrtbase.dll` (C runtime), which the VTune top-down tree places entirely under `read_data_points`, for example when parsing the `.dat` files.
To compare with gprof, which does not see that time, the distance and selection columns are shares of the kNN time only (I/O excluded).
The gprof columns are from the summary table above.

| Scenario | k | Type | VTune CPU time (s) | Samples (≈) | I/O (% of total) | Distances, VTune | Distances, gprof | Selection, VTune | Selection, gprof |
|---|---|---|---|---|---|---|---|---|---|
| WISDM | 3 | double | 0.41 | 41 | 14 % | 90 % | 100 % | 10 % | 0 % |
| | 3 | float | 0.39 | 39 | 13 % | 92 % | 91 % | 8 % | 9 % |
| | 5 | double | 0.53 | 53 | 12 % | 75 % | 83 % | 25 % | 17 % |
| | 5 | float | 0.50 | 50 | 12 % | 57 % | 74 % | 43 % | 26 % |
| | 20 | double | 0.93 | 93 | 7 % | 40 % | 30 % | **60 %** | **70 %** |

### Main observations

- **VTune confirms the gprof hotspots.** In every configuration the top two functions are `get_*_NN` and `select_*_nearest` and the selection becomes the largest hotspot for WISDM with k = 20 in both tools.
  The top-down tree also confirms the call graph: `select_*_nearest` is called from `get_*_NN`, which is called from `knn_classifyinstance*`.
- **The two tools agree within the sampling error.**
- **File reading is a real cost that gprof hides.**
- **Small functions are not sampled:** `minmax_normalize_point`, `copy_*_nearest`, `plurality_voting*`.

### Limitations

- The runs are too short for precise percentages; repeating each run several times or using a shorter sampling interval (`--interval 1`) could help reduce the error.
- Hardware event-based sampling was not used since only user-mode sampling was available.
